What XON Solves

Multi-agent AI systems have no standard for what passes between agents. XON is that standard.

Problem

  • Context lost between agents
  • Decisions untracked and unverifiable
  • No human window into agent reasoning
  • No standard handoff format
  • Agents must be trained per-format

XON Answer

  • Structured context travels with the file
  • Full decision chain preserved and compressed
  • Rich HTML rendering for humans, YAML for agents
  • Open spec, any agent can implement
  • Self-describing: spec baked into every file

Who Uses It

  • AI agent pipeline developers
  • Research teams running multi-agent workflows
  • Enterprises automating document pipelines
  • Humans reviewing AI-generated documents
  • Any system exchanging structured context

Container Structure

A `.xon` file is a ZIP archive. Every entry has a defined role and audience.

document.xon ← ZIP container (DEFLATE)
│
├── manifest.yaml required ← index, lineage, version, file registry
│
├── spec/
│ ├── xon.md required ← full spec travels with file
│ ├── agent-guide.md required ← ~800 token agent injection guide
│ └── schemas/ optional ← JSON Schema validation files
│
├── shared/
│ └── data.yaml required ← canonical facts (agents + humans read this)
│
├── agent/ ← machine audience only
│ ├── context.md required ← task for current agent
│ ├── output-schema.json required ← what agent must return
│ ├── state.yaml required ← current pipeline state
│ ├── decision-chain.yaml required ← provenance (tiered compression)
│ └── next-agent-brief.md optional ← instructions for next agent
│
└── human/ ← human audience only
├── index.html optional ← HTML fragment (no script tags)
├── index.txt optional ← plain text fallback
├── styles.css optional ← agent-generated styles
├── patches.yaml optional ← human text edits (out-of-band)
└── assets/ optional ← SVG, images, fonts

Agent Output Modes

The SDK accepts three output modes from agents. The required mode is declared in agent/output-schema.json.

Data Update

data-update

Agent returns updated structured fields only. SDK re-renders the existing HTML with new data via binding substitution. Design is preserved from the previous agent pass.

Use for: extraction, validation, decision agents

Designed

designed

Agent returns data and symbolic visual directives (theme, accent colour, layout, highlighted fields). SDK generates HTML from the directives using the template library.

Use for: agents with design intent, no raw HTML needed

Full HTML

full-html

Agent returns data, a complete HTML fragment, CSS, and SVG assets. Full design independence. SDK sanitises and packages. No script tags permitted.

Use for: report generators, first XON creation, creative documents

Security Model

Two enforcement layers — SDK validates before packaging, app sandboxes at render time.

SDK Layer (before packaging)

  • Strip all <script> tags from agent HTML
  • Strip on* event handler attributes
  • Strip javascript: URI schemes
  • Strip <iframe>, <object>, <embed>, <form>
  • Block external CSS url() imports
  • Validate output against output-schema.json
  • Validate patches.yaml (plain text content only)

App Layer (at render time)

  • Document WebView fully sandboxed (no Tauri IPC)
  • CSP: script-src 'none' for document webview
  • Agent CSS scoped — cannot style app chrome
  • xon:// protocol serves from in-memory ZIP only
  • postMessage bridge validates type + origin
  • Edit content sanitised (plain text only)
  • File system inaccessible from document webview
