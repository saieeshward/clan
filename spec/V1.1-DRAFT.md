> 1. Hints emit on **stderr** (the diagnostic stream), not stdout — `clan read data` output stays parseable YAML.

## 22. Agent-Only Flow — The Preservation Rule

A CLAN chain is **lossless** iff every hop preserves all five context layers. Each layer is optional to *read* but mandatory to *preserve*:

| # | Layer | Member(s) |
|---|---|---|
| 1 | Distilled state | `shared/data.yaml` |
| 2 | Working transcript / scratchpad | `agent/context.md`, `agent/state.yaml`, optional `agent/transcript/` |
| 3 | Contracts | `agent/output-schema.json` |
| 4 | Provenance | `agent/decision-chain.yaml` |
| 5 | Capability requirements | `agent/requirements.yaml` (new, optional) |

**The pass-through rule (normative):** an agent or SDK that consumes only a subset of layers MUST carry all other layers forward unmodified into the child file. `pack`, `pack-html`, and all `patch-*` operations already satisfy this by construction; any third-party implementation MUST too.

### agent/requirements.yaml (new, optional)

Tool *implementations* are framework-resident and cannot portably travel. CLAN carries the **declaration** instead, so a receiving framework can check capability fit before running the next hop:

```yaml
requires:
  tools:
    - name: web_search
      why: "verify vendor registration numbers"
    - name: code_execution
      why: "recompute totals"
  model_hints:
    min_context_tokens: 64000
```

Receiving orchestrators SHOULD warn (not fail) on unmet requirements.

## 23. Deferred Rendering

The structured members (§22 layers 1–5) are canonical. The human view (`human/`) is a **derivable artifact**: any conforming implementation can materialise it from the structured members at any point in the chain. Pure agent-to-agent chains skip rendering at every hop; the last hop — or a human's tooling — renders once.

### manifest.yaml: `view` field (amends §5)

```yaml
view:
  present: false        # human/index.html exists in this file
  renderable: true      # a view CAN be produced from current structured members
  stale: false          # present but produced from an older data.yaml generation
```

Rules:
- `present: false, renderable: true` — agent-only file; render on demand.
- `stale: true` is set automatically by any `patch-data`/`pack` that changes `shared/data.yaml` without updating the view.
- A file with `present: true` MUST render without error from its own members (the §24 invariant guarantees `data.yaml` is always single-valued, hence always bindable).

### CLI

- `clan create --no-render` / `clan pack --no-render` — produce agent-only files (`present: false`).
- `clan render <file>` — materialise `human/` from structured members (invokes an agent or applies the default theme renderer); sets `present: true, stale: false`.

Render-per-hop workflows are unchanged: omit `--no-render` and behaviour is identical to v1.0.

## 24. Fork/Join Concurrency

Concurrency model: **isolate writes, then deterministically fold.** No locks, no CRDTs, no merge servers. This mirrors the per-branch isolation + per-key reducer model that production frameworks ship (LangGraph reducers; CrewAI async/context joins) — expressed as files.

### 24.1 `clan fork`

```
clan fork parent.clan --agents researcher,analyst,critic --output-dir branches/
```

Produces one child per agent. Each child:
- carries the full parent content (pass-through rule);
- gains a manifest `fork` block naming its writer:

```yaml
fork:
  agent_id: researcher
  namespace: agents/researcher/
  forked_from: <parent sha256>
```

**Namespace rule (normative):** on a forked file, the named agent MUST write only inside `agents/<agent_id>/` (`data.yaml`, `context.md`, `decisions.yaml`, `assets/`). Writes to `shared/data.yaml` or `agent/` are **rejected by the CLI** with a teaching error (§27). Conflicts are thereby impossible by construction during the parallel interval.

### 24.2 Multi-parent lineage (amends §13)

```yaml
lineage:
  parents:
    - id: <uuid>          # branch 1 (researcher)
      sha256: <hash>
      delta: "market findings"
    - id: <uuid>          # branch 2 (analyst)
      sha256: <hash>
      delta: "risk scores"
  merge: true
```

The v1.0 single-parent form remains valid and is equivalent to a one-element `parents[]`.

### 24.3 `clan merge`

```
clan merge branches/*.clan --output merged.clan
```

Folds every branch's `agents/<id>/data.yaml` into `shared/data.yaml`, deterministically, using per-key policies declared in the manifest:

```yaml
merge_policies:
  default: last-write          # by decision-chain timestamp
  keys:
    findings: append           # concatenate lists
    risk_score: max
    status: last-write
    summary: agent-priority    # order given in fork block
```

Branch `decisions.yaml` entries are appended to the merged `decision-chain.yaml` in timestamp order. Branch namespaces are retained in the merged file (provenance; cheap — ZIP-deflated) unless `--prune-namespaces`.

The merge is **mechanical — no LLM call required.** Token cost of the whole fan-out: each branch agent reads the shared base once plus its own namespace; no agent ever reads a sibling's transcript.

### 24.4 merge-report.yaml

Every key where two or more parents wrote **different values** is recorded, regardless of which policy won:

```yaml
generated_by: clan merge v1.1.0
conflicts:
  - key: status
    winner: { value: "approved", agent: analyst, policy: last-write }
    losers:
      - { value: "needs-review", agent: critic }
    decision_refs: [analyst@2026-06-10T14:02Z, critic@2026-06-10T14:01Z]
unresolved: 1   # decremented as adjudications land (§25)
```

Conflicts are **data, not failures**: `clan merge` exits 0 with conflicts present (exits non-zero only on structural errors), prints the contested-key count, and emits a §27 hint pointing at adjudication.

## 25. Conflict Adjudication

**Invariant (normative): `shared/data.yaml` is never ambiguous.** Merge always produces exactly one value per key. No inline conflict markers, no multi-values — the UI bindings (`{{key}}`) and downstream injection both depend on this. Losing values survive in branch namespaces and `merge-report.yaml`.

Adjudication protocol — identical for humans and agents:
1. Read `merge-report.yaml` (injected automatically when unresolved > 0, §26).
2. Choose a value → `clan patch-data` with the chosen value.
3. Record it → `clan patch-decision --agent <id> --action "adjudicated <key>" --rationale "..."`.
4. The CLI removes the key from `merge-report.yaml` and decrements `unresolved`.

Viewer behaviour: elements whose binding key appears in `merge-report.yaml` are badged (contested-value indicator); the badge surfaces competing values with agent provenance; the human's pick runs the same protocol via the existing patch bridge. Conflicts are rendered, not erased.

## 26. Conditional Context Injection (amends §15)

The base agent guide (`spec/agent-guide.md`, ~800 tokens) is **byte-stable** across all files and hops — never edited per file (prompt-cache-friendly). Situational knowledge is appended *after* it as small blocks, selected by **file state**, so an agent never reads about a capability its current file doesn't exhibit:

| Condition (from manifest / members) | Injected block | Budget |
|---|---|---|
| `fork` block present | "You are branch agent `<id>`. Write only inside `agents/<id>/`. Your writes merge later via manifest `merge_policies`." | ≤ 80 tokens |
| `merge-report.yaml` with `unresolved > 0` | The report itself (TOON) + the 4-step adjudication protocol (§25) | report + ≤ 60 tokens |
| `view: {present: false, renderable: true}` | "No human view exists. Produce one with `clan render` / `pack-html` only if your task requires it." | ≤ 30 tokens |
| `agent/requirements.yaml` present | The requirements block (TOON) | as-is |
| none of the above | nothing | 0 |

A sequential agent on an unforked, conflict-free file receives exactly the v1.0 injection — zero added cost for the common case.

## 27. Teachable Interface (Progressive Disclosure Protocol)

**Principle: every command teaches the next step; nothing teaches ahead of need.** An agent learns the CLAN protocol through the outputs of the commands it actually runs. An agent that never forks never hears about merging.

### 27.1 Hint blocks

Every CLI command MAY append a hint block to its stdout, after its primary output:

```
next: clan read agent merged.clan        # assemble your task context
next: 2 contested keys in merge-report.yaml — adjudicate with patch-data + patch-decision
```

Normative properties:
- **Deterministic.** `hint = f(command, result, file state)` — same inputs, same hint. Testable.
- **Bounded.** ≤ 3 lines, ≤ ~40 tokens per command. Hints are headlines, not documentation; each names the command that gives the detail.
- **Stable prefix.** Every hint line starts `next:` (machine-strippable). `--quiet` or `CLAN_NO_HINTS=1` suppresses all hints; output parsers and orchestrators rely on this.
- **Precondition-gated.** A hint MUST NOT mention a capability whose preconditions are absent from the current file state: no merge hints on unforked files, no adjudication hints when `unresolved == 0`, no render hints when `present: true, stale: false`.

### 27.2 Errors teach (guardrails as documentation)

Every guardrail rejection MUST name the correct alternative in the same message:

```
error: this file is forked for agent 'researcher' — direct writes to shared/data.yaml are
       not allowed during a parallel interval.
next:  clan patch-data file.clan '<patch>' --namespace   # writes to agents/researcher/data.yaml
```

For agents, the error message *is* the documentation. Conventions that rely on agents remembering prose fail (v1.0 `structured:` trap, 75% first-try failure rate); commands that correct on contact succeed.

### 27.3 Reference hint map (initial)

| Command / event | Hint |
|---|---|
| `create` success | `next: clan read agent <file>` |
| `read agent` on forked file | `next: write only to agents/<id>/ — patch-data routes there automatically` |
| `pack` success, `view.present: false` | `next: file is agent-only; clan render <file> materialises the human view when needed` |
| `pack`/`patch-data` success, view now stale | `next: human view is stale — clan render <file> to refresh` |
| `fork` success | per-branch: `next: you are <agent_id>; your namespace is agents/<agent_id>/` |
| `merge` success, conflicts > 0 | `next: <n> contested keys in merge-report.yaml — clan read report <file>, then patch-data + patch-decision to adjudicate` |
| `merge` success, conflicts = 0 | `next: clean merge — clan read agent <file> to continue` |
| `patch-data` on a contested key | `next: '<key>' was contested at merge — record your adjudication with patch-decision` |
| `validate` pass on `renderable` file | `next: structured members valid; view optional (clan render)` |

### 27.4 Consequence for the base guide

As the hint map covers protocol mechanics at point of use, the byte-stable base guide SHOULD shrink over minor versions (target: ≤ 400 tokens by v1.2) to its irreducible core: what you received, what you must return, the schema contract. Everything procedural moves to the channel where it is actionable — the command output.

## Deferred to v1.2 (recorded, not specified)

- Event-log / append-only delta state (state = fold of per-hop delta records) — the principled successor to namespace merge; changes every reader.
- Delta-per-hop injection (`read agent --since <parent-sha>`) — inject only namespace writes + decision entries new since the parent snapshot. Falls out of §24 structure; needs measurement first (research/13 open question 2).
- LLMLingua-style compression, key interning, schema-default omission — unverified savings; no numbers may be claimed without a dedicated research pass (research/13 thread 3).
