CLAN

Context & Live Agent Notation

Not a framework. Not a runtime. A file format.

Multi-agent pipelines break at the handoff. State lives in whichever runtime is running, so when work passes to a different model, team, or tool, the reasoning stays behind. CLAN fixes the artifact, not the runtime — a .clan file is a plain ZIP that carries the task, the attributed decision history, the output contract, and a self-rendering human view. Everything a fresh agent needs to continue without a briefing.

The problem

Intelligence gets stranded at the boundary

An AI pipeline produces briefs, reports, contracts, clinical notes. When the artifact crosses a handoff, the intelligence that shaped it — the rationale, the field-level attribution, the human overrides, the output contract — stays behind in a platform database or an evicted context window. The document moves; the reasoning doesn't. Why does this field say X? can't be answered from the artifact itself.

Ad-hoc handoff

  • Provenance lives in the framework's memory — lost on export
  • No output contract travels; the next agent guesses the shape
  • Parallel agents collide on shared state; merges cost LLM tokens
  • Human edits are indistinguishable from model output
  • A fresh agent needs a human to re-brief it

A .clan file

  • Every mutation is attributed at write time — rejected if not
  • The JSON-Schema output contract lives inside the file, validated on write
  • Parallel agents write to isolated namespaces; merge is deterministic, zero LLM tokens
  • Human edits land back as edited_by: human patches
  • The file carries its own spec — any agent can resume cold

CLAN makes provenance a structural property of the artifact rather than a feature of the platform. The core inversion: intelligence belongs to the artifact, not the runtime.

What it looks like

A standard ZIP — open it with anything

A .clan file is an ISO 21320-1 ZIP archive (MIME application/vnd.clan) of plain UTF-8 text. A typical file is 30–80 KB on disk; the decision chain is capped at ~10–15 KB regardless of pipeline length.

my-document.clan ← a standard ZIP ├── manifest.yaml identity · lineage · file registry + SHA-256 ├── spec/ │ ├── clan.md the full spec, embedded in every file │ └── agent-guide.md byte-stable protocol guide (~800 tok) ├── shared/ │ └── data.yaml canonical facts — one source of truth ├── agent/ │ ├── context.md the current agent's task │ ├── output-schema.json JSON Schema — validated at pack time │ ├── state.yaml pipeline state │ └── decision-chain.yamlevery decision, attributed + compressed ├── agents/ per-agent namespaces (parallel work) │ └── <agent-id>/ writes outside your namespace = rejected ├── merge-report.yaml contested keys, both sides, with provenance └── human/ ├── index.html the human view, inside the artifact ├── patches.yaml human edits, edited_by: human └── assets/

Four reserved layers, four audiences — kept strictly apart so agents skip human markup and the viewer collapses agent internals:

spec/The format itself. Every file is self-describing, so an agent that has never seen CLAN can still produce valid output.
shared/Canonical typed data, read by agents and bound into the human view via {{key}}. No duplication anywhere else.
agent/Machine content: task, contract, state, and the append-only decision chain.
human/The rendered, editable document — derivable from shared/, never the source of truth.

Examples · how it works

Any language can read and write it

There's no CLAN runtime and no CLAN cloud — the format is just ZIP + YAML + JSON. The open-source Rust CLI and SDK are the reference implementation. Here's a full pipeline.

1

Create a document from a brief

Bootstraps the ZIP with the embedded spec, an output-schema stub, and an empty decision chain.

clan create --title "Q3 Market Analysis" \
  --brief "Evaluate CRM options for a 40-person agency" --output doc.clan
next: clan read agent doc.clan
2

Hand the whole context to an agent

One optimized prompt: the guide, task, contract, TOON-encoded data and a distilled decision tail — assembled lazily, human markup never read.

clan read agent doc.clan     # full accumulated context, TOON-encoded
3

Write one field — with attribution

A surgical RFC 7396 merge patch. Omit --agent/--action and it's refused.

clan patch-data doc.clan \
  --set "verdict=HubSpot" \
  --agent analyst --action "set verdict" --rationale "best fit for budget"

clan read chain doc.clan       # full attributed decision history
clan validate doc.clan         # check the output contract, any time
4

Run agents in parallel, then merge

Each branch writes only its own namespace; the merge is deterministic and reports every contested key with both sides' provenance.

clan fork doc.clan --agents researcher,analyst --output-dir branches

clan patch-data branches/researcher.clan --namespace \
  --set "finding=market is growing" --agent researcher --action research
clan patch-data branches/analyst.clan --namespace \
  --set "risk=vendor lock-in" --agent analyst --action analyze

clan merge branches/*.clan --output merged.clan
# Deterministic. Zero LLM tokens. Contested keys → merge-report.yaml

Twenty-plus subcommands cover the full lifecycle — render, pack-html, patch-html (selector-targeted DOM edits), patch-schema, patch-asset, export-static (a single JSON blob for SDK-less agents), and agent-help (a <200-token protocol card for AI operators).

Core guarantees

The hard parts, solved by design

Not conventions an application politely follows — invariants the reference CLI enforces the way a JSON parser rejects malformed syntax.

✎

Attribution or rejection

A mutation without --agent and --action is refused. Every write records who, what, why, when, and the exact fields_changed. Provenance is enforced at write time, not bolted on.

⇉

Fork · isolate · fold

Fork a file into one branch per agent. Each writes only inside its agents/<id>/ namespace — collisions are impossible by construction. clan merge is a deterministic per-key fold. Zero LLM tokens.

⚖

Conflicts are data

Contested keys don't fail the merge — they land in merge-report.yaml with the winner, every loser, and both sides' provenance. Policies: last-write, append, max, min, agent-priority.

{ }

Living output contract

A real JSON Schema ships inside the file and is validated against the merged data on every write. Change a field's shape without migrating the schema and the CLI hard-rejects the patch, before it can break the view.

⊟

TOON-encoded context

On the way into an agent's prompt, data and history are serialised as TOON — ~40% fewer tokens than JSON, 51–58% on tabular data. Provably lossless, or it falls back to raw JSON.

↻

Bounded memory

The 5 newest decisions stay verbatim; older rationales are compressed by a deterministic, model-free keyword pipeline (pinned entries never). The chain stays ~10–15 KB whether the pipeline is 3 hops or 30.

◱

Self-rendering view

The human-readable document lives in the artifact. A Tauri desktop viewer renders it with click-to-edit; edits return as attributed human patches, part of the same provenance chain.

?

Self-teaching CLI

Every command prints a gated next: hint; every rejection names the fix in the same breath. In tests, agents told only "there's a clan CLI — figure it out" reached correct usage in under 4 commands, zero violations.

⛓

Verifiable lineage

Each file records its parent's UUID and SHA-256; every member carries a checksum of its uncompressed bytes. The chain back to origin is cryptographically walkable — and merges record every parent.

Where CLAN loses

  • Short chains. The scaffolding — schema, chain, guide — is overhead with no payoff under ~4 hops. If your pipeline is short and your prompts are disciplined, ad-hoc is leaner on raw input size.
  • The synthesis-hop result isn't robust. 0.487× one run, 1.047× the next. It's in the scorecard, marked red.
  • Provenance is only as truthful as the agents. CLAN records who acted and when — it can't verify an agent's account of what it did. Run a verifier hop where fidelity matters.
  • Wall-time savings are modest — ~12–18% on 8–10 hop chains. Token savings don't dominate latency.

The bottom line, in the project's own words: CLAN's price is a modest, bounded token overhead; its product is that correctness, provenance, conflict detection and human attribution survive even when nobody writes a careful prompt — the regime real multi-framework pipelines live in. The format, not the prompt, carries the protocol.

Where it fits

Multi-stakeholder, regulated, resumable work

The mechanics are identical across domains — gather, analyze, decide — only the template and data schema differ. Provenance matters most exactly where an artifact crosses organizational boundaries and someone may later ask why.

Legal

intake → draft → negotiated → executed

Records why a clause changed and who approved it — the answer you need if a contract is ever disputed.

Medical

intake → diagnosis → treatment → follow-up

Continuity of care and liability need the why, not just the what. On-prem inference for HIPAA via a key-proxy pattern.

Finance

research → analysis → recommendation → approved

Under MiFID II, Reg BI and FINRA, examination becomes a read operation on the artifact's intelligence layer.

Engineering

requirements → spec → design-review

A traceability matrix that records why a requirement moved — merged, de-scoped, or a stakeholder changed their mind.

Creative / Ad-tech

brief → concept → deck

One file metamorphoses across schema migrations while every prior hop survives verbatim in the lineage.

Any agent handoff

gather → analyze → decide

Regulator-readable, cold-resumable, framework-agnostic — a common artifact across LangChain, CrewAI, AutoGen or your own stack.

Verified, not asserted

Dogfooded and tested in the open

The intro explainer and the benchmark report are themselves .clan files — the strongest proof point is that CLAN ships its own docs as provenance-native artifacts.
